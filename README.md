# File Network

**From file paths to meaningful connections.**

파일을 폴더 경로가 아닌 내용과 의미, 관계를 중심으로 탐색하는 로컬 기반 파일 관리·분석 시스템입니다.

File Network는 PC에 저장된 파일을 스캔하고 메타데이터를 로컬 데이터베이스에 관리합니다. 현재 텍스트·소스 코드·PDF·DOCX·XLSX·PPTX의 내용 추출과 본문 검색을 제공하며, 공유 키워드 기반 관련 문서 탐색·그래프를 제공하고 생성형 AI 기반 질의응답·비교 기능으로 확장하는 것을 목표로 합니다.

---

## 1. 프로젝트 소개

기존 파일 시스템에서는 사용자가 파일의 저장 위치나 폴더 경로를 기억해야 원하는 파일을 찾기 쉽습니다.

File Network는 파일의 위치뿐 아니라 메타데이터와 문서 내용, 파일 간 연관성을 활용해 파일을 탐색하는 환경을 만드는 프로젝트입니다.

핵심 설계 원칙은 **파일 관리와 데이터 저장은 로컬 엔진이 담당하고, 생성형 AI는 사용자가 허용한 데이터에 대해서만 분석을 수행한다**는 것입니다.

### 주요 목표

- PC 내 파일 메타데이터 통합 관리
- 파일 생성·수정·삭제·이동 감지
- 키워드 및 의미 기반 파일 검색
- 문서 내용 분석 및 파일 간 관계 발견
- 생성형 AI를 활용한 문서 요약, 비교, 질의응답
- 파일 간 관계를 시각적으로 탐색

## 2. 시스템 구성 및 역할

File Network는 로컬 엔진을 중심으로 동작하며, 생성형 AI는 선택적으로 연결하는 분석 모듈로 설계합니다.

| 구성 요소 | 역할 |
|---|---|
| File Scanner | 디렉터리 재귀 탐색 및 파일 메타데이터 수집 |
| Incremental Scan | 기존 DB 정보와 비교해 신규·수정·변경 없는 파일 구분 |
| Change Tracker | 파일 삭제 및 이동 추적 |
| Local Database | 파일 메타데이터, 스캔 상태 및 분석 결과 저장 |
| Search Engine | 키워드 및 향후 의미 기반 검색 |
| AI Service | 허용된 문서 데이터의 요약·비교·질의응답 |
| UI | 검색 결과, 파일 정보 및 AI 분석 결과 제공 |

### 데이터 처리 흐름

```text
사용자 요청
    |
    v
로컬 엔진
    |
    +--> 파일 검색 및 DB 조회
    |
    +--> 필요한 문서 내용 추출
    |
    +--> 민감정보 검사 및 전송 대상 선별
                 |
                 v
        사용자 전송 승인
                 |
                 v
        외부 생성형 AI API
                 |
                 v
          분석 결과 반환
                 |
                 v
       로컬 엔진에서 결과 검증
                 |
                 v
          사용자에게 제공
```

AI가 파일 시스템이나 SQLite에 직접 접근하지 않습니다. AI는 로컬 엔진이 전달한 제한된 데이터만 분석하며, DB의 실제 변경은 로컬 엔진이 검증한 뒤 수행하도록 설계합니다.

## 3. AI 활용 및 보안 정책

생성형 AI를 활용하되 로컬 파일의 보안과 사용자의 데이터 통제권을 우선합니다.

### 3.1 AI 활용 범위

향후 생성형 AI를 통해 다음 기능을 제공하는 것을 목표로 합니다.

- **문서 질의응답:** 사용자가 선택하거나 검색한 문서를 근거로 질문에 답변
- **문서 요약:** 긴 문서의 핵심 내용과 주요 항목 정리
- **문서 비교:** 여러 문서의 공통점, 차이점 및 변경 사항 분석
- **관계 분석:** 프로젝트·주제·키워드 등을 바탕으로 관련 파일 탐색 지원
- **자연어 검색:** 일상적인 문장으로 파일을 검색할 수 있도록 지원

### 3.2 로컬 우선 처리 원칙

- 파일 원본은 사용자의 로컬 파일 시스템에 유지합니다.
- 파일 메타데이터와 검색 데이터베이스는 로컬에서 관리합니다.
- 파일 스캔, DB 조회, 검색 대상 선정은 로컬 엔진에서 수행합니다.
- 외부 AI API는 사용자가 AI 분석을 요청한 경우에만 사용합니다.
- AI가 DB에 직접 접속하거나 파일을 임의로 수정하지 못하도록 역할을 분리합니다.

### 3.3 외부 API 데이터 전송 정책

외부 생성형 AI API를 사용할 때는 다음 정책을 적용하는 것을 목표로 합니다.

1. **최소 데이터 전송:** 분석에 필요한 문서 일부와 문맥만 선별해 전송합니다. 원본 파일 전체를 기본적으로 전송하지 않습니다.
2. **사용자 승인:** 외부 전송 전에 대상 파일과 전송할 내용을 확인하고 승인할 수 있도록 합니다.
3. **민감정보 보호:** 개인정보, 인증정보, 기밀정보 등이 포함된 데이터는 탐지 후 기본적으로 전송을 차단하거나 로컬 분석만 허용합니다.
4. **비식별화:** 분석에 불필요한 이름, 연락처, 식별 정보 등은 가능한 범위에서 마스킹하거나 대체합니다. 단, 마스킹만으로 재식별 위험이 완전히 사라지는 것은 아닙니다.
5. **전송 범위 통제:** 사용자가 선택한 파일과 검색 결과 중 필요한 데이터만 전송합니다.
6. **API 키 보호:** API 키를 소스 코드나 저장소에 포함하지 않고 환경변수 또는 안전한 비밀정보 관리 방식을 사용합니다.
7. **전송 기록 관리:** 전송 여부와 대상 등 필요한 기록을 남기되, 민감한 원문이 로그에 불필요하게 저장되지 않도록 합니다.
8. **제공 업체 정책 확인:** API 제공 업체의 데이터 보관, 학습 사용 여부, 삭제 및 처리 정책을 확인한 뒤 사용합니다.

### 3.4 로컬 전용 모드

외부 API 사용을 원하지 않는 사용자를 위해 외부 전송을 비활성화할 수 있는 로컬 전용 모드를 지향합니다.

- 로컬 파일 스캔 및 DB 관리는 계속 사용할 수 있어야 합니다.
- 로컬에서 가능한 검색과 분석 기능은 외부 API 없이 동작하도록 설계합니다.
- 외부 AI 분석 기능은 비활성화하거나 사용할 수 없음을 명확히 표시합니다.

> **중요:** 외부 API로 데이터를 전송하는 순간 전송된 데이터에 대한 제3자 처리 위험이 발생할 수 있습니다. 일부 데이터만 보내거나 마스킹하더라도 보안이 완전히 보장되는 것은 아닙니다. 민감하거나 기밀인 문서는 외부 전송을 차단하는 것을 기본 원칙으로 합니다.

## 4. 파일 분석 정책

모든 파일을 네트워크에 등록하되, 파일 유형과 접근 가능 여부에 따라 분석 수준을 구분합니다.

| 파일 유형 | 분석 방향 |
|---|---|
| TXT, MD, CSV 등 텍스트 | 메타데이터 및 텍스트 내용 분석 |
| PDF, DOCX, PPTX, XLSX | 메타데이터 및 문서 내용 추출 |
| 소스 코드 | 메타데이터 및 코드 내용 분석 |
| 이미지·동영상·음성 | 우선 메타데이터 중심으로 관리 |
| 압축 파일 | 우선 파일명 및 메타데이터 중심으로 관리 |
| 실행 파일 및 바이너리 | 파일명 및 메타데이터 중심으로 관리 |
| 접근 불가 파일 | 접근 가능한 정보만 수집하고 오류 상태 기록 |

내용을 추출할 수 없는 파일도 파일 메타데이터를 관리할 수 있는 범위에서 네트워크에 포함하는 것을 목표로 합니다.

## 7. 실행 방법

Windows 실행 배포본은 **7.14**를 참고하세요. Python·Git 없이 압축을 풀고 실행할 수 있습니다. 아래 7.1~7.13은 소스 실행/개발 안내입니다.

### 7.1 사전 요구 사항

- Python 3.12 권장 (Linux·macOS·Windows CI 검증 버전)
- Git
- Windows 명령 프롬프트(CMD), PowerShell 또는 macOS/Linux 터미널

### 7.2 저장소 복제

```bash
git clone https://github.com/wjddydghks/file-network.git
cd file-network
```

### 7.3 가상환경 생성

**Windows CMD**

```cmd
py -m venv .venv
```

**Windows PowerShell**

```powershell
py -m venv .venv
```

**macOS / Linux**

```bash
python3 -m venv .venv
```

### 7.4 가상환경 활성화

**Windows CMD**

```cmd
.venv\Scripts\activate
```

**Windows PowerShell**

```powershell
.\.venv\Scripts\Activate.ps1
```

PowerShell에서 실행 정책 오류가 발생하면 현재 사용자 범위에서 스크립트 실행 정책을 확인해야 합니다. CMD를 사용하면 위의 PowerShell 실행 정책 문제를 피할 수 있습니다.

**macOS / Linux**

```bash
source .venv/bin/activate
```

정상적으로 활성화되면 터미널 프롬프트 앞에 `(.venv)`가 표시됩니다.

### 7.5 패키지 설치

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 7.6 테스트용 디렉터리 생성

프로젝트 폴더와 스캔 대상 폴더는 분리하는 것을 권장합니다.

**Windows CMD**

```cmd
mkdir "%USERPROFILE%\file-network-test"
echo Hello File Network > "%USERPROFILE%\file-network-test\test.txt"
```

**Windows PowerShell**

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\file-network-test"
Set-Content "$env:USERPROFILE\file-network-test\test.txt" "Hello File Network"
```

**macOS / Linux**

```bash
mkdir -p "$HOME/file-network-test"
echo "Hello File Network" > "$HOME/file-network-test/test.txt"
```

### 7.7 프로그램 실행

명령어는 반드시 **프로젝트 루트(`file-network`) 디렉터리에서** 실행합니다.

**Windows CMD**

```cmd
python -m app.main "%USERPROFILE%\file-network-test"
```

**Windows PowerShell**

```powershell
python -m app.main "$env:USERPROFILE\file-network-test"
```

**macOS / Linux**

```bash
python -m app.main "$HOME/file-network-test"
```

실행 시 지정한 디렉터리를 스캔하고 파일 메타데이터를 로컬 SQLite 데이터베이스에 저장합니다.

소스 실행의 기본 데이터베이스 위치:

```text
database/file_network.db
```

### 7.8 실행 시 주의 사항

- `python -m app.main`은 프로젝트 루트에서 실행해야 합니다.
- 스캔 대상 경로는 실제로 존재하는 디렉터리여야 합니다.
- Windows CMD에서는 Linux의 `~` 및 `$HOME` 문법을 사용하지 않습니다.
- Windows CMD에서 사용자 홈 경로는 `%USERPROFILE%`로 지정합니다.
- 프로젝트 코드 폴더 전체를 무심코 스캔하지 말고 별도의 테스트 디렉터리로 먼저 검증하는 것을 권장합니다.
- Windows 등의 파일 시스템에서 파일 식별자가 SQLite 정수 범위를 넘는 경우에도 정밀도를 보존해 저장합니다. 범위 초과 값은 `int:` 접두사의 텍스트로 저장하고 앱의 DB 연결에서 정수로 복원합니다. 기존 DB 삭제나 재생성은 필요하지 않습니다.

### 7.9 내용 추출·DB 저장·검색

`app.main`은 메타데이터 수집만 수행합니다. 변경·삭제·이동 추적은 `app.incremental_scan`을 사용하고, 본문까지 분석하려면 `app.analyze_content`를 사용합니다.

**Windows CMD**

```cmd
python -m app.extract_text "%USERPROFILE%\file-network-test\example.pdf" --max-bytes 10485760
python -m app.analyze_content "%USERPROFILE%\file-network-test" --max-bytes 10485760
python -m app.search_content "Hello" --limit 10
python -m app.search_content "보고서" --target name --limit 10
python -m app.search_content "보고서" --target all --limit 10
python -m app.analyze_content "%USERPROFILE%\file-network-cp949" --encoding cp949
```

**macOS / Linux**

```bash
python -m app.extract_text "$HOME/file-network-test/example.pdf" --max-bytes 10485760
python -m app.analyze_content "$HOME/file-network-test" --max-bytes 10485760
python -m app.search_content "Hello" --limit 10

python -m app.search_content "보고서" --target all --limit 10
python -m app.analyze_content "$HOME/file-network-cp949" --encoding cp949
```

- 예시의 CP949 폴더 경로는 실제 해당 인코딩으로 저장된 텍스트 폴더로 바꿔 사용합니다.
- 단일 파일 추출은 JSON을 출력합니다. 일괄 분석은 먼저 증분 스캔한 뒤 본문·분석 상태·사유를 `file_contents`에 저장합니다. 원본은 수정하지 않습니다.
- 텍스트·코드의 기본 `--encoding auto`는 UTF-8(UTF-8 BOM 포함)과 BOM이 있는 UTF-16 LE/BE·UTF-32 LE/BE를 지원합니다. CP949는 `--encoding cp949`로 직접 선택합니다. `--encoding utf-8`은 UTF-8만 허용합니다. BOM 없는 UTF-16/UTF-32나 CP949를 자동 추정하지 않으며, 잘못된 바이트는 대체 문자로 덮어쓰지 않고 실패로 기록합니다. 디코딩된 NUL 문자는 바이너리로 제외하고 원본 줄바꿈은 보존합니다. 입력 크기 제한에는 BOM도 포함합니다. 인코딩 선택은 해당 분석 폴더의 텍스트·코드 전체에 적용하므로 서로 다른 인코딩이 섞인 폴더는 분리해 분석하거나 UTF-8 사본을 사용하세요. PDF·Office에는 적용하지 않습니다. PDF는 PyMuPDF로 텍스트 레이어를 페이지 순서대로 추출하고 페이지 사이를 폼 피드(`\f`)로 구분합니다. 페이지 끝 줄바꿈은 정규화하며 표·레이아웃을 원본 그대로 복원하지는 않습니다.
- PDF와 Office도 기본 입력 크기 제한은 1 MiB이며 `--max-bytes`로 늘릴 수 있습니다. PDF 추출기의 기본 제한은 200페이지, 출력 1,000,000자입니다.
- 암호가 필요한 PDF는 `ENCRYPTED_PDF`, 이미지 전용 PDF는 `OCR_REQUIRED`, 본문이 없는 PDF는 `NO_TEXT`로 건너뜁니다. 손상 PDF는 `INVALID_PDF` 실패 사유로 기록합니다. 텍스트 페이지와 무텍스트 이미지 페이지가 섞이면 읽을 수 있는 본문을 저장하고 `PARTIAL_OCR_REQUIRED` 사유를 남깁니다. OCR·암호 입력은 아직 제공하지 않습니다.
- DOCX는 본문 문단·표·중첩 표를 읽고, XLSX는 값이 있는 시트의 이름·셀 값·수식 문자열을 읽습니다. 수식을 계산하거나 외부 링크를 따라가지 않습니다. PPTX는 슬라이드별 텍스트·표·그룹 도형의 글자를 읽습니다. 세 형식 모두 한글을 지원합니다.
- Office 추출기의 기본 제한은 압축 해제 크기 합계 64 MiB, 내부 항목 10,000개, 출력 1,000,000자, XLSX 셀 범위 100,000개, PPTX 200슬라이드입니다. XLSX는 선언된 범위 및 읽은 셀/빈 행을 제한에 포함하므로 서식만 넓게 잡힌 문서도 제한에 걸릴 수 있습니다.
- 파일 암호화 및 구형 OLE 컨테이너는 `ENCRYPTED_OFFICE` 또는 `ENCRYPTED_OR_LEGACY_OFFICE`로 건너뜁니다. 손상 문서는 `INVALID_OFFICE` 실패로 기록하며 다른 파일의 분석은 계속합니다.
- 구형 `.doc`·`.xls`·`.ppt`, 매크로 전용 확장자, Word 머리글·꼬리글·각주·주석, PPT 노트·차트·SmartArt 내용, 문서 내 이미지 OCR은 아직 추출하지 않습니다. 표·셀 좌표·서식·시각적 레이아웃을 그대로 복원하는 기능은 아닙니다.
- 상태는 `EXTRACTED`·`SKIPPED`·`FAILED`로 구분합니다. 실패 파일은 다음 실행에서 재시도하며 크기 제한·텍스트 인코딩 선택·추출기 버전 또는 원본 메타데이터가 바뀌면 재분석합니다. 인코딩 변경으로 PDF·Office 캐시를 무효화하지는 않습니다. PDF·Office 등 추출기 지원 업데이트 후 기존 캐시는 한 차례 재분석될 수 있습니다.
- 변경·삭제가 스캔에서 확인되면 이전 본문을 비우고 `STALE`로 표시합니다. 같은 확장자의 이동은 파일 ID와 본문을 유지합니다. 내용 해시는 사용하지 않으므로 모든 비교 메타데이터가 동일한 내용 변경은 감지하지 못합니다.
- 기본 본문 검색은 저장된 활성 파일의 `EXTRACTED` 본문만 대상으로 합니다. 여러 검색어는 AND로 처리하며 `--root`로 디렉터리 범위를 제한할 수 있습니다. 관련도·현재 경로·일치 미리보기를 JSON으로 반환합니다. 한국어 형태소·임의 부분 문자열·의미 검색은 아직 제공하지 않습니다.
- `--target name`은 스캔된 활성 파일의 이름(확장자 포함)을 부분 문자열로 검색합니다. 본문 미분석·건너뜀·실패 파일도 포함하며 원본을 읽지 않습니다. 여러 단어는 AND로 처리하고 한글 정규화·유니코드 대소문자 무시를 적용합니다. `%`, `_`, 따옴표도 일반 문자입니다. 디렉터리 이름·본문은 검색하지 않으며 결과는 경로순입니다. `--root`·`--limit`을 지원하고 JSON의 `snippet`은 파일명, `score`는 0입니다. 새 파일·이름 변경·삭제는 다시 스캔한 뒤 반영됩니다.
- `--target all`은 본문과 파일명을 함께 검색합니다. 본문 일치를 기존 관련도순으로 우선 표시하고 파일명만 일치하는 결과를 경로순으로 추가합니다. 같은 파일은 한 번만 표시하며 `--limit`은 합친 전체 결과에 적용합니다. 각 대상 안에 검색어가 모두 있어야 하며 파일명·본문에 단어를 나눠 포함한 경우는 일치하지 않습니다. 통합 JSON에는 표시한 일치 위치인 `match_source`(`content`/`name`)를 추가합니다. 두 대상 모두 일치하면 본문을 표시합니다. 기본값은 기존 본문 검색이며 단독 본문/파일명 검색의 결과 형식은 그대로입니다.
- 본문 분석 실패가 있으면 종료 코드 1, 성공·건너뛰기는 0입니다. 잘못된 인자는 2이며 지원하지 않는 문서 형식은 메타데이터만 관리합니다.
- `Ctrl+C`로 증분 스캔을 취소하면 세션을 `CANCELLED`로 기록하고 코드 130으로 종료합니다. 취소 전 완료된 DB 변경은 유지됩니다. 강제 종료·전원 차단 시 중단된 세션 복구는 후속 작업입니다.
- 이동·삭제 건수는 스캔 이력에 저장하며 CLI에서 활성 파일 수와 전체 레코드 수를 구분합니다. 내용 분석은 로컬에서 처리하고 외부 AI API를 호출하지 않습니다.

1. **폴더 선택**으로 분석할 디렉터리를 고릅니다. 경로를 직접 입력할 수도 있습니다.
2. **스캔·분석**을 누르면 메타데이터 스캔과 본문 분석을 백그라운드에서 수행합니다. GUI의 파일별 크기 제한은 기본 10 MiB이며 변경할 수 있습니다. 인코딩 선택의 기본값은 **자동 (BOM·UTF-8)**입니다. CP949 한글 텍스트는 **CP949 (한글 Windows)**를 선택한 뒤 분석합니다. 이 선택은 폴더의 텍스트·코드 전체에만 적용하며 PDF·Office에는 적용하지 않습니다.
3. 완료 후 검색 대상을 **본문**, **파일명**, **통합 (본문·파일명)** 중에서 선택하고 검색어를 입력한 뒤 **검색** 또는 Enter를 누릅니다. 기본은 선택 폴더 범위이며 **모든 분석 폴더**을 켜면 저장된 전체 범위를 검색합니다.
4. **분석 내역 보기**를 누르면 선택 폴더와 하위 디렉터리의 파일별 처리 결과를 조회합니다. 상태 선택에서 완료·건너뜀·실패·재분석 필요·미분석을 필터링하고, 파일을 선택하면 사유와 오류·대응 안내를 확인합니다. **모든 분석 폴더**와 **최대 결과** 설정은 내역 조회에도 적용합니다. 삭제된 파일은 제외하며 내역 조회 자체는 원본을 읽거나 재분석하지 않습니다.
5. 검색 결과를 선택하면 현재 경로와 일치 본문을 미리 봅니다. 파일명 검색에서는 일치한 파일명을 표시하며 본문 추출 여부와 무관하게 찾을 수 있습니다. 통합 검색은 **일치 위치** 열과 미리보기에서 본문/파일명을 구분합니다. **원본 파일 열기** 또는 결과 더블클릭은 OS 기본 연결 앱을 사용합니다. **저장된 본문 보기**를 누르면 마지막 분석 결과를 별도 읽기 전용 창에서 확인합니다. 검색 결과·선택 행은 유지하며 분석 상태·사유·시각을 함께 표시합니다. 본문은 한 번에 최대 100,000자씩 불러오며 **이전 구간 / 다음 구간**으로 저장된 나머지 본문도 읽습니다. 전체 글자 수·현재 구간·글자 범위를 표시합니다. 구간은 원본 문서 페이지가 아닌 글자 수 기준입니다. **처음부터 새로 읽기**는 최신 DB 결과를 첫 구간부터 조회합니다. 구간 이동 중 재분석 결과가 바뀌면 이전 본문을 지우고 새로 읽기를 안내합니다. **현재 표시 구간에서 찾기**와 **이전 일치 / 다음 일치**는 해당 구간 안에서 문자열을 찾고 끝에서 순환합니다. Ctrl+F(macOS는 Cmd+F)로 찾기 입력에 초점을 옮깁니다. 구간 경계를 가로지르는 일치나 다른 구간의 단어는 이 찾기의 대상이 아닙니다. 본문이 없는 파일은 상태와 사유를 표시합니다. 최신 원본이 아닌 저장된 분석 결과이며, 원본을 다시 읽거나 재분석하지 않습니다. 변경·삭제가 스캔에서 확인된 이전 본문은 표시하지 않습니다. 원본 페이지·표 레이아웃을 복원하는 문서 뷰어는 아닙니다.
6. **취소**를 누르면 협력적으로 중단합니다. PDF 페이지·Office 문단/행/도형 등 처리 경계에서 취소를 확인하며, 현재 I/O·파서 호출·검색·DB 처리가 반환되기까지는 잠시 걸릴 수 있습니다. 이미 저장이 끝난 결과는 유지하고 취소된 문서의 부분 본문·인용은 저장하지 않습니다. 작업 중 창을 닫아도 중단·스레드 종료를 기다린 뒤 닫습니다.

분석·검색·본문 조회 중에는 중복 실행을 막기 위해 입력을 잠급니다. 취소·오류 후에는 다시 사용할 수 있으며 처리 건수, 건너뜀·실패 수를 표시합니다. 파일을 다시 스캔·분석하기 전에는 마지막으로 저장한 내역을 표시합니다. 분석 시각은 저장된 ISO 형식의 시간대와 함께 표시합니다. 폴더·인코딩·검색 옵션은 로컬 설정으로 저장·복원하며 Windows 개발용 실행 배포본은 7.14에서 안내합니다. 기존 CLI와 같은 로컬 DB를 사용하고 외부 AI API를 호출하지 않습니다.

GUI 자동 테스트는 `QT_QPA_PLATFORM=offscreen` 환경에서 실제 텍스트/PDF 엔진 연계, 결과 선택·열기 요청, 화면 응답·취소·창 닫기를 검증합니다. 기본 의존성만 설치한 환경에서는 GUI 테스트가 생략되며, GitHub Actions는 GUI 의존성을 설치하고 세 OS에서 엔진·GUI 테스트를 모두 실행합니다.

### 7.12 선택 실행: 대용량 텍스트 분석 벤치마크

```bash
python -m benchmarks.content_analysis --files 10000
python -m benchmarks.content_analysis --dataset mixed --files 600 --output benchmark-mixed.json
```

기본 `text` 프로필은 실제 UTF-8 텍스트 파일과 DB를 별도의 임시 디렉터리에 만들어 최초 분석·캐시 재분석·첫 본문 검색을 검증하고 JSON으로 시간, DB 연결 수, 처리 건수, Python/OS/SQLite 정보를 출력합니다. 사용자 파일이나 기본 DB는 사용하지 않으며 종료 시 임시 데이터를 정리합니다. 기본 파일 수는 1,000개이고 `text`는 1~100,000개를 지정할 수 있습니다. 앱 실행에서는 자동으로 실행하지 않습니다.

`--dataset mixed`는 UTF-8·BOM UTF-16 텍스트, 2페이지 PDF, 문단/표 DOCX, 시트/수식 XLSX, 2슬라이드 PPTX를 순환 생성합니다. 18~10,000개를 지정하며 600개이면 각 형식 100개입니다. 전체 본문 색인 건수와 형식별 검색을 확인하고, 각 형식 1개씩 수정·별도 파일 1개 이동·PDF 1개 삭제 후 수정 검색어 반영, 기존 검색어 제거, 이동 ID 보존, 삭제 본문 무효화와 다음 실행의 캐시 재사용을 검증합니다. 구형 Office·OCR·암호화·손상 문서는 이 표본에 포함하지 않습니다.

JSON에는 형식별 개수·입력 크기·검증 결과가 추가되며 `--output`으로 UTF-8 보고서를 저장할 수 있습니다. 보고서는 집계 결과만 포함하고 원문·임시 경로를 넣지 않습니다. Windows CI는 회귀 테스트 후 `mixed` 600개를 추가 실행하고 **mixed-document-benchmark-Windows** artifact에 JSON만 7일간 보관합니다. Actions 실행의 Windows 작업 로그와 artifact에서 실제 runner 환경·결과를 확인할 수 있습니다. 시간 임계값으로 성공/실패를 정하지 않으며 실제 파일 처리 결과로 검증합니다.

내부 DB 연결은 `with db.get_connection()` 범위를 벗어날 때 커밋/롤백 후 닫힙니다. 직접 연결을 얻는 코드는 기존처럼 명시적으로 `close()`합니다. 이 처리로 예외 traceback이 남아도 Windows에서 임시 DB 파일 핸들이 유지되지 않도록 합니다. 임시 데이터 경로도 생성 전에 정규화해 macOS 경로 별칭과 Windows 짧은 경로를 일관되게 검증합니다.

캐시 상태는 본문을 읽지 않고 최대 500개씩 조회합니다. 기존 파일별 결과 저장·실패 재시도·취소 시 완료된 결과 보존은 유지하며 캐시 형식이나 추출기 버전은 바꾸지 않습니다.

개발 Linux 환경(Python 3.12.14, SQLite 3.53.1)의 짧은 텍스트 표본 측정:

| 조건 | 개선 전 | 개선 후 |
|---|---:|---:|
| 3,000개 캐시 재분석 DB 연결 | 3,015회 | 21회 |
| 동일 cProfile 방식의 재분석 시간 | 0.5844초 | 0.2619초 |

개선 후 10,000개를 별도 실행한 표본에서는 최초 10,000개 추출 15.492초, 재분석 10,000개 캐시 재사용 0.364초/DB 연결 49회, 첫 검색 20개 결과 0.021초였습니다. 시간은 단일 환경의 예시이며 OS 캐시를 비우지 않았습니다. 실제 문서 크기·디스크·파일 시스템·백신·OS에 따라 달라지므로 이전 `text` 프로필의 Linux 표본이며 Windows나 혼합 PDF/Office 폴더의 성능을 보장하는 수치가 아닙니다. 혼합 프로필 및 Windows CI 보고서 역시 작은 합성 문서의 특정 실행 환경 표본이므로 사용자 실제 PC·복잡한 대형 문서의 성능과 구분해야 합니다. 최초 분석의 파일별 DB 저장, 스캔 메타데이터 전체 보관, 대용량 개별 문서·네트워크 드라이브 성능은 별도 검증 범위입니다.

### 7.13 GUI 설정 저장·복원

마지막 입력 폴더, 텍스트 인코딩, 파일 크기 제한, 검색 대상(본문/파일명/통합), 모든 분석 폴더 선택, 최대 결과 수, 분석 상태 필터를 저장합니다. 변경 후 약 0.3초 동안 입력이 없으면 저장하며 폴더 직접 입력은 편집 완료 시, 닫기는 진행 중인 작업의 종료를 기다린 뒤 최종 값을 반영합니다. 재실행 시 설정만 복원하고 분석·검색은 자동으로 시작하지 않습니다. 검색어·본문·결과·인증정보는 설정에 저장하지 않습니다.

파일은 Qt의 OS 표준 `GenericConfigLocation` 아래 `file-network/gui-settings.json`에 UTF-8 JSON으로 저장합니다. 일반적인 위치는 다음과 같으며 OS 사용자 설정에 따라 달라질 수 있습니다.

- Windows: `%LOCALAPPDATA%\file-network\gui-settings.json`
- Linux: `$XDG_CONFIG_HOME/file-network/gui-settings.json` 또는 `~/.config/file-network/gui-settings.json`
- macOS: `~/Library/Preferences/file-network/gui-settings.json`

설정은 최대 64 KiB로 읽고 버전·자료형·값 범위를 확인합니다. 손상되거나 지원하지 않는 버전은 기본값으로, 잘못된 개별 필드는 해당 항목만 기본값으로 복원하고 화면 하단에 안내합니다. 경로가 없어져도 시작 시 폴더를 생성하거나 스캔하지 않으며 실제 분석/검색 요청 시 경로를 확인합니다. 설정을 읽지 못한 상태에서 단순 실행·종료만으로 원본 설정을 덮어쓰지는 않습니다.

저장은 임시 파일을 완성한 뒤 원자적으로 교체합니다. 저장 실패 시 기존 파일을 유지하고 화면에서 안내하며 앱 사용이나 닫기를 막지 않습니다. **설정 초기화**는 화면 설정을 기본값으로 되돌려 저장하며 원본 파일·DB·분석 결과를 삭제하지 않습니다. CLI 옵션과 동작에는 영향을 주지 않습니다.

### 7.14 Windows 실행 배포본 (Python 설치 없이 실행)

[Windows Desktop Build](https://github.com/wjddydghks/file-network/actions/workflows/desktop.yml)를 **Run workflow**로 수동 실행하면 선택한 브랜치의 세 OS 테스트가 성공한 뒤 Windows 배포본을 빌드·실행 검증합니다. 성공한 수동 실행의 **FileNetwork-Windows-x64** artifact를 내려받습니다. 일반 PR·main CI에서는 테스트만 진행하며 EXE·ZIP을 새로 만들지 않습니다. GitHub 로그인이 필요할 수 있으며 artifact는 14일 보관합니다.

1. ZIP의 **모든 파일**을 한 폴더에 압축 해제합니다.
2. **FileNetwork.exe**를 실행합니다. `_internal` 폴더를 지우거나 EXE만 따로 옮기면 실행되지 않습니다.
3. 폴더 선택 → 스캔·분석 → 본문/파일명/통합 검색 → 저장된 본문 보기 또는 원본 열기 순서로 사용합니다.
4. 기존 소스 실행 DB는 자동 이동하지 않으므로 처음 배포본을 쓰면 대상 폴더를 다시 스캔·분석합니다.

실행 배포본 DB는 `%LOCALAPPDATA%\file-network\file_network.db`에 저장합니다. 환경 변수가 없으면 사용자 홈의 `AppData/Local/file-network`를 사용합니다. 실행 파일 폴더/임시 번들 폴더에 DB를 만들지 않으며 소스 실행의 `database/file_network.db`도 그대로 유지합니다. 화면 설정 경로는 7.13과 같습니다. 업데이트는 앱을 닫고 새 ZIP을 별도 폴더에 풀어 실행하면 사용자 데이터가 유지됩니다.

현재 Windows x64 **개발용 미서명 배포본**입니다. Windows Server 2022 CI에서 검증하며 사용자 PC의 OS/조직 보안 정책에 따라 실행이 제한될 수 있습니다. 코드 서명·설치 마법사·자동 업데이트는 아직 제공하지 않습니다. 포함 라이브러리의 메타데이터와 라이선스도 `_internal/*.dist-info`에 함께 보관합니다.

개발자가 직접 빌드하려면 Windows에서 다음을 실행합니다. 타 OS에서 빌드하면 해당 OS 실행 파일이 생성되며 Windows 교차 빌드는 지원하지 않습니다.

```bash
python -m pip install -r requirements-build.txt
python -m PyInstaller --noconfirm --clean FileNetwork.spec
python scripts/verify_desktop.py dist/FileNetwork/FileNetwork.exe --report package-smoke-Windows.json
```

검증 도구는 Python 환경변수를 제거하고 최소 시스템 PATH 및 빈 외부 작업 폴더에서 **빌드된 실행 파일**을 실행합니다. Windows에서는 실제 `windows` Qt 플랫폼으로 GUI 분석·검색·미리보기·설정 복원을 검사하고 합성 혼합 문서 18개의 추출/캐시/검색/수정·이동·삭제도 검사합니다. 실제 사용자 파일/DB/설정은 사용하지 않습니다. 성공한 배포 폴더만 artifact로 올리며 **desktop-verification-Windows**에는 집계 JSON을 보관합니다. 모든 사용자 PC의 실행을 보장하는 깨끗한 VM 설치 검증을 대신하는 것은 아닙니다.

### 7.15 문서 인용 단위와 원본 위치

폴더를 **스캔·분석**한 뒤 검색 결과의 **저장된 본문 보기**에서 **인용 단위 · 원본 위치**를 선택합니다. 이전/다음으로 최대 2,000자씩 확인하며, PDF는 추출 시 기록한 실제 페이지 번호를 표시합니다. 빈 페이지·이미지 전용 페이지도 실제 페이지 순서에 포함하므로 2페이지 다음 인용이 4페이지일 수 있습니다. 이 번호는 1부터 시작하는 물리적 페이지 순서이며 문서에 인쇄된 쪽 번호와 다를 수 있습니다. OCR을 수행하거나 원본 레이아웃을 복원하지 않습니다.

XLSX는 **실제 시트명**, PPTX는 **실제 슬라이드 번호**를 표시하고 인용이 시트·슬라이드 경계를 넘지 않습니다. 빈 시트·슬라이드는 인용할 텍스트가 없어 표시되지 않지만 슬라이드 번호는 실제 순서를 유지합니다. 위치는 추출기가 기록한 구조 정보이며 본문의 `시트:`·`슬라이드:` 문자열로 추정하지 않습니다.

텍스트·코드·DOCX는 **추출 본문 문자 위치**를 표시하며 페이지 번호를 추정하지 않습니다. 인용 단위는 글자 수로 분할하므로 문장·단어·수식 경계가 나뉠 수 있습니다. PDF 인용은 실제 페이지 경계를 넘지 않으며 페이지 사이 구분 문자는 인용에서 제외합니다. 공백·빈 페이지에는 인용할 텍스트가 없을 수 있습니다.

검색 CLI 결과의 `file_id`로도 조회할 수 있습니다.

```bash
python -m app.document_chunks 1
python -m app.document_chunks 1 --chunk 2
```

`--chunk`는 1부터 시작합니다. JSON의 `segment`와 `start_char`는 0부터 시작하며 `end_char`는 포함하지 않습니다. `text`는 저장된 전체 본문의 `[start_char:end_char]`와 일치합니다. `page`는 PDF 실제 페이지 번호이며 다른 형식은 `null`입니다. `source_kind`는 `page`(PDF)·`sheet`(Excel)·`slide`(PowerPoint)·`text`(일반 문자 위치)이며, `source_label`은 시트명 또는 슬라이드 번호 문자열입니다. PDF·일반 문자 위치의 레이블은 `null`입니다. `file_id`·`analyzed_at`·`source_fingerprint`와 인용 번호로 분석 시점의 근거를 구분합니다. 이전 결과의 `analyzed_at` 값을 `--revision`에 전달하면 다른 분석 버전의 내용을 섞어 읽지 않도록 거부합니다.

인용 데이터는 로컬 DB의 `document_chunks`에 문자 범위만 저장하고 본문을 중복 저장하지 않습니다. 파일 변경·삭제가 스캔에서 확인되거나 재분석되면 이전 인용을 제거하며, 동일 확장자의 파일 이동은 기존 ID와 인용을 유지합니다. 인용 조회는 원본을 다시 열지 않는 **마지막 분석 시점의 스냅샷**입니다. 실제 원본이 바뀌었는지는 폴더를 다시 분석해서 확인하세요. 외부 API 전송은 없습니다.

업데이트해도 기존 DB·본문은 보존합니다. 이전 버전에서 분석한 문서는 인용 정보가 없으므로 폴더를 한 번 다시 **스캔·분석**하세요. 추출기 버전 변경으로 기존 분석 캐시를 다시 생성하며, 이후 변경 없는 파일은 인용과 본문을 함께 재사용합니다. 이전 Office 인용은 재분석 전까지 문자 위치로 유지되며, 재분석하면 시트·슬라이드 위치가 추가됩니다. 의미 검색·문장 단위 청킹·Word 페이지·Excel 셀 좌표·슬라이드 도형 좌표 인용은 후속 범위입니다.

#### 검색 결과에서 일치 인용 바로 보기

본문 검색 결과를 선택하고 **일치 인용 보기**를 누르면 모든 검색어가 포함된 **첫 인용 단위**를 엽니다. PDF 페이지·Excel 시트·PowerPoint 슬라이드 등 저장된 원본 위치도 함께 표시합니다. 검색창을 편집했더라도 마지막으로 완료한 검색 결과의 검색어를 사용합니다. 파일명 전용 검색·통합 검색에서 파일명만 일치한 결과·분석 내역에서는 이 버튼을 사용하지 않습니다.

본문 검색과 같은 `unicode61` 토큰화 및 리터럴 AND 규칙을 사용합니다. 전체 문서에서는 모든 단어를 찾았더라도 서로 다른 인용 단위에 나뉘어 있거나 인용 경계에서 단어가 나뉘면 일치 인용이 없을 수 있습니다. 이때 결과 목록은 유지하며 **저장된 본문 보기**로 전체 내용을 확인할 수 있습니다. 이전 버전에서 인용을 만들지 않은 문서는 폴더를 다시 분석하세요. 인용 창의 **이전/다음 구간**은 검색 일치 여부와 무관하게 원래 인용 순서대로 이동합니다.

선택 문서의 본문을 한 DB 스냅샷에서 한 번 읽고, 인용 순서대로 최대 128개씩 메모리에 임시 색인합니다. 첫 일치를 찾으면 뒤쪽 처리를 중단하고, 못 찾은 묶음은 비운 뒤 다음 묶음을 검색합니다. 영구 DB에 본문·색인을 추가 저장하지 않습니다. 전체 본문을 한 번 메모리에 읽는 비용은 남으며, 끝부분/미일치는 필요한 인용을 모두 순회하므로 큰 문서는 시간이 걸릴 수 있습니다. 원본 파일을 다시 열거나 외부 API를 호출하지 않습니다. SQLite 처리 중 취소를 확인하며, 검색 후 미리보기 사이 분석 버전이 바뀌면 서로 다른 분석 내용을 섞어 표시하지 않습니다.

### 7.16 폴더명으로 스캔·분석 제외하기

GUI의 **분석 제외 폴더**에 `.git, node_modules, .venv`처럼 쉼표로 구분한 폴더명을 입력하고 **스캔·분석**합니다. 기본값은 비어 있으며 자동으로 제외하는 폴더는 없습니다. 설정은 다른 GUI 옵션과 함께 저장·복원되고 **설정 초기화**로 비울 수 있습니다.

- 지정한 이름과 **전체 일치**하는 하위 폴더는 모든 깊이에서 순회하지 않습니다. `node_modules-old` 같은 비슷한 이름이나 같은 이름의 파일은 제외하지 않습니다.
- 선택한 분석 루트 자체는 이름이 같아도 분석합니다. Windows는 대소문자를 구분하지 않고 macOS/Linux는 입력한 대소문자를 구분합니다.
- 경로·와일드카드는 지원하지 않습니다. 예를 들어 `C:\Windows`, `../cache`, `*.git` 대신 폴더명만 입력합니다. 최대 100개이며 이름당 최대 255자입니다. 쉼표가 포함된 이름은 이번 입력 형식으로 지정할 수 없습니다.
- 제외한 폴더의 **기존 DB·본문·인용은 보존**합니다. 해당 파일은 이번 실행의 변경·삭제·이동 후보 및 본문 분석에서 제외합니다. 제외는 기존 검색 결과를 숨기거나 DB 용량을 줄이는 기능이 아닙니다. 오래된 검색 결과가 남을 수 있습니다.
- 제외를 지우고 다시 분석하면 그 범위의 변경·삭제 판정을 재개합니다. 제외된 폴더에서 밖으로 옮긴 파일은 기존 제외 레코드의 ID를 가져오지 않고 새 파일로 등록합니다.
- 제외는 분석할 폴더의 선택 옵션입니다. 접근 오류와 달리 의도한 분석 범위 밖이므로 나머지 범위의 정상적인 삭제 판정은 계속합니다. 취소·접근 오류가 발생한 불완전 스캔의 오삭제 방지 동작은 유지합니다.

기본 스캔·증분 스캔·본문 분석 CLI는 `--exclude-dir`를 반복해서 지정합니다.

```bash
python -m app.main "C:/Users/me" --exclude-dir node_modules --exclude-dir .venv
python -m app.incremental_scan "C:/Users/me" --exclude-dir node_modules --exclude-dir .venv
python -m app.analyze_content "C:/Users/me" --exclude-dir node_modules --exclude-dir .venv
```

세 스캔·분석 CLI의 표준 출력·오류는 UTF-8을 사용하므로 Windows에서 파이프나 파일로 전달할 때도 한글 출력 때문에 중단되지 않습니다.

CLI 제외 옵션은 해당 실행에만 적용하며 GUI 설정과 공유하지 않습니다. 전체 PC 분석은 우선 필요한 문서·프로젝트 폴더부터 진행하는 것이 좋습니다. 이 기능이 수십만~수백만 파일 규모의 속도나 메모리 사용량을 보장하는 것은 아닙니다.

앱이 현재 사용하는 DB의 **정확한 경로**와 SQLite의 `-journal`·`-wal`·`-shm` 보조 경로는 기본 스캔·증분 스캔·본문 분석 및 GUI에서 자동 제외합니다. DB가 선택한 루트 안에 있어도 자기 파일을 등록하거나 반복 분석하지 않습니다. 파일 정보 접근 전에 제외하므로 일시적으로 생겼다 없어지는 SQLite 보조 파일도 수집하지 않습니다. 같은 이름의 다른 폴더에 있는 사용자 DB나 비슷한 파일명은 제외하지 않습니다. 이전 버전에서 이미 등록한 내부 파일의 메타데이터·본문 상태는 다른 제외 설정처럼 보존하며, 이번 분석·이동·삭제 판정에서는 다루지 않습니다. 원본 DB를 삭제하거나 비우지 않습니다.

### 7.17 파일명 검색용 값 재사용

파일명 검색은 NFC·Unicode casefold로 정규화한 이름을 DB에 저장하고 재사용합니다. 신규 파일·이름 변경·이동 시 갱신하므로 검색할 때마다 모든 파일명을 Python으로 다시 정규화하지 않습니다. 기존 DB는 처음 실행 시 500개씩 읽어 검색용 값을 채우며 파일 ID·본문·인용은 유지합니다. 최초 갱신 동안에는 DB 쓰기 작업이 발생하고 큰 DB는 시간이 걸릴 수 있습니다. 부분 문자열 검색 자체는 여전히 후보 파일을 순회하므로 수십만~수백만 파일에서 일정한 응답 시간을 보장하지 않습니다. 기존 Unicode·리터럴 부분 일치·검색 결과 순서는 유지합니다.

### 7.18 공유 키워드로 관련 문서 탐색

검색 결과나 분석 내역에서 파일을 선택하고 **관련 문서 보기**를 누릅니다. 저장된 본문이 있는 활성 파일을 기준으로 다른 문서를 찾습니다. 결과 표와 미리보기에 **실제로 겹치는 키워드**를 표시하며, **저장된 본문 보기**·**일치 인용 보기**로 근거를 확인하거나 후보를 선택해 관련 문서를 계속 탐색할 수 있습니다. 미분석·미지원·재분석 필요 파일은 먼저 분석을 완료해야 합니다. 취소·오류 시 기존 결과 목록을 유지합니다.

기본 후보 범위는 현재 선택한 폴더와 하위 폴더이며 **모든 분석 폴더**를 켜면 DB 전체에서 찾습니다. 기준 문서 자체는 결과에서 제외합니다. **최대 결과** 값을 사용하되 관련 문서는 최대 100개입니다. 파일명이 같거나 비슷한 것만으로는 후보에 포함하지 않습니다.

```bash
python -m app.related_documents 1
python -m app.related_documents 1 --limit 10 --root "C:/Users/me/Documents"
```

JSON에는 기준 파일 ID·경로·분석 시각, 선정 키워드와 빈도/문서 빈도/가중치, 후보의 공유 키워드·본문 발췌·분석 시각을 반환합니다. `relation_type`은 `shared_keywords`입니다.

선정 규칙은 기존 본문 FTS와 같은 `unicode61` 토큰화로 기준 문서를 읽고 2~64자 토큰 중 출현 빈도 상위 256개를 후보로 삼습니다. 제한된 공통어 목록과 순수 숫자를 제외하고, 다른 문서에도 등장하는 단어를 `기준 문서 출현 수 × log(1 + 전체 분석 문서 수 / 해당 단어의 문서 수)`로 정렬해 최대 8개를 고릅니다. 후보 문서는 이 키워드의 **OR 검색**을 BM25·경로 순서로 정렬합니다. 동의어·한국어 형태소 분석·임베딩은 사용하지 않으며, 짧거나 공통어 위주인 문서는 결과가 없을 수 있습니다. 선정과 빈도 통계는 전체 색인을 기준으로 하되 후보 반환에 폴더 범위를 적용합니다.

**공유 키워드가 있다는 근거를 제공하는 후보 탐색**이며 의미가 같거나 실제 업무 관계가 있다고 확정하지 않습니다. 실제 문서 비교·AI 관계 분석은 후속 범위이며, 공유 키워드 관계 그래프는 7.19에서 안내합니다.

원본을 다시 열거나 외부 API를 호출하지 않습니다. 본문 검색과 같은 영구 FTS를 재사용하고, 기준 문서 토큰화용 색인과 어휘 조회는 메모리 임시 테이블로 만들었다가 연결 종료 시 해제합니다. 기존 본문 색인이 없다면 최초 조회 시 초기화합니다. 조회는 한 DB 읽기 스냅샷에 연결하며 결과는 마지막 분석 시점의 자료입니다. 큰 기준 문서는 임시 색인에 시간과 메모리가 필요할 수 있습니다.

### 7.19 공유 키워드 관계 그래프

먼저 **관련 문서 보기**를 실행한 뒤 **관계 그래프**를 누릅니다. 기준 문서를 중앙에, 관련 결과의 상위 후보를 최대 20개만 주변에 표시합니다. 목록에 100개가 있어도 그래프는 기준 문서 1개와 후보 20개까지 표시하며, 후보가 없으면 기준 문서만 표시합니다. 그래프를 열기 위해 원본을 재분석하거나 DB·외부 네트워크를 조회하지 않습니다.

- **문서 또는 연결선 선택:** 아래에 문서 경로·분석 시각·공유 키워드·저장된 본문 발췌를 표시합니다. 선의 툴팁에서도 공유 키워드를 확인합니다.
- **문서 두 번 클릭 / 선택 문서 본문 보기:** 그래프를 닫고 해당 문서의 저장된 본문을 엽니다. 후보 목록에 없는 기준 문서도 열 수 있습니다. 후보를 열면 관련 결과 목록에서 해당 행도 선택합니다.
- **문서 선택** 콤보로 키보드에서도 같은 문서·근거를 선택합니다.
- 휠·**확대/축소**로 크기를 바꾸고 빈 공간 드래그로 이동합니다. **화면 맞춤**으로 전체 구조를 다시 봅니다.

연결선은 기존 관련 결과에 기록된 **기준 문서↔후보의 공유 키워드 근거**만 표시합니다. 후보끼리의 관계·방향성·인과관계를 추정하지 않습니다. 키워드 후보 그래프이며 의미 유사성·실제 업무 관계를 확정하지 않습니다. 그래프와 목록은 마지막 관련 조회 시점의 스냅샷입니다. 본문을 열 때 분석 시각을 검사하여 재분석된 다른 버전의 내용을 섞어 표시하지 않으며, 최신 관계는 **관련 문서 보기**를 다시 실행해 확인합니다.

**선택 문서 중심으로**를 누르면 선택한 후보의 관련 문서를 백그라운드로 다시 조회하고 새 그래프를 엽니다. 현재 기준 문서에는 이 버튼을 비활성화합니다. 각 단계는 처음 관련 조회에서 사용한 폴더 범위와 건수 제한을 유지하며, 그래프에 범위를 표시합니다. 새 중심의 결과도 상위 20개만 그립니다. 조회 중에는 기존 작업 취소·안전한 창 닫기가 적용되며 실패·취소 시 이전 그래프와 목록·기록을 유지하고 그래프 위에 사유를 안내합니다.

**이전 그래프**는 DB 재조회 없이 이전 기준·후보 목록·범위를 저장된 스냅샷에서 복원합니다. 기록은 실행 중 메모리에 최대 10개만 보관하고 파일·DB·설정에는 저장하지 않습니다. 닫았다 다시 연 그래프에서도 같은 탐색 기록을 사용할 수 있습니다. 새 검색·분석·분석 내역 조회를 시작하거나 일반 **관련 문서 보기** 조회를 새로 완료하면 기록을 초기화합니다. 복원한 결과도 과거 조회 시점의 데이터이므로 최신 관계는 새 조회로 확인하세요. 한 번에 여러 단계를 펼치는 그래프가 아니라 사용자가 한 단계씩 중심을 바꾸는 탐색입니다.

기존 `PySide6 Essentials`의 `QGraphicsView`를 사용합니다. Qt WebEngine·웹 서버·CDN·브라우저·외부 API와 새 영구 그래프 데이터는 필요하지 않습니다. 여러 단계를 동시에 펼치는 다중 홉 그래프, 의미 검색 관계, 자동 레이아웃·내보내기는 후속 범위입니다.

### 7.20 MVP 안정화 점검 기록

앱 DB가 분석 루트 안에 있을 때 자기 DB를 등록하고 매번 재처리하던 문제를 수정했습니다. 실제 WAL 보조 파일이 열린 상태, 정확한 경로와 비슷한 사용자 파일의 구분, 기존 내부 레코드 보존, 501개 문서에서 스캔 취소 후 재실행과 수정·삭제 반영을 자동 검증합니다. 실행 파일 자체 검증의 합성 자료도 DB를 분석 루트 안에 두어 같은 상황을 검사합니다.

현재 코드의 단일 Linux 환경에서 **합성 소형 UTF-8 문서 10,000개**를 생성해 전체 추출·색인과 재실행 캐시를 확인했습니다. 첫 분석 약 17.64초, 재실행 약 0.40초, 첫 검색 약 0.023초였고 DB는 약 7.0 MiB(저장 본문 348,890자·인용 10,000개)였습니다. 혼합 문서 600개도 추출·색인·캐시·수정 6개/이동 1개/삭제 1개 처리를 검증했습니다. 재현 명령은 7.12와 같으며 보고서에는 `database_bytes`·`stored_text_chars`·`citation_chunks`도 포함합니다.

위 수치는 OS 캐시를 초기화하지 않은 합성 소형 자료의 단일 환경 기록입니다. 실제 사용자 문서, 큰 개별 파일, 전체 드라이브의 수십만~수백만 파일에서의 시간·메모리·DB 용량을 보장하지 않습니다. 실사용 PC의 문서 점검과 최종 배포본 검증은 별도로 남아 있습니다.

### 7.21 큰 문서 처리 중 취소와 제한

분석 중 취소 요청은 파일 사이뿐 아니라 PDF 페이지, Word 문단·표, Excel 시트·행·셀 값 조합, PowerPoint 슬라이드·도형·문단 처리 경계에도 전달합니다. 파일 읽기와 파서 시작/종료·본문 조합 경계에서도 확인하며, 추출 뒤 DB 저장 직전에 다시 확인합니다. 취소를 파싱 실패로 기록하지 않고 작업 중단으로 전파합니다.

취소된 현재 문서는 부분 본문·인용을 저장하지 않습니다. 이미 저장이 끝난 파일은 유지하며 다음 실행에서 완료된 캐시를 재사용하고 미완료 파일을 다시 분석합니다. 수정되어 기존 본문이 무효화된 파일은 재분석 전까지 재분석 필요 상태로 남을 수 있습니다. 분석 시각/본문 형식·인용 경계 규칙은 그대로이므로 기존 캐시를 이 변경 때문에 강제로 재생성하지 않습니다.

이 방식은 협력적 취소입니다. 디스크 읽기, 라이브러리의 문서 열기, 한 페이지/행을 파싱하는 호출 내부를 강제 종료하지 않으므로 해당 호출이 반환되기까지는 기다릴 수 있습니다. GUI에서 창을 닫는 경우에도 같은 취소 경로로 작업 종료를 기다립니다.

기본 제한을 넘는 합성 개별 문서도 검사합니다. 1 MiB를 넘는 텍스트(기본 추출 한도), PDF 201페이지, Word 1,000,001자, Excel 선언 범위 100,001셀, PowerPoint 201슬라이드는 각 크기/출력/페이지/셀/슬라이드 제한 사유로 건너뛰고 부분 결과를 반환하지 않습니다. GUI의 파일당 입력 크기 기본값은 기존처럼 10 MiB이며, PDF/Office 내부 제한은 별도로 적용합니다. 제한 안의 모든 실제 복잡 문서에 대한 처리 시간·메모리 상한을 보장하는 것은 아닙니다.

### 7.22 긴 문서 인용 조회 안정화

기존 인용 조회는 SQLite `substr`로 긴 본문을 인용마다 반복해서 읽고, 첫 일치가 앞에 있어도 모든 인용을 먼저 임시 색인했습니다. 본문을 한 번 읽고 기존 문자 오프셋으로 나누어 128개씩 검색하도록 변경했습니다. 첫 일치에서 멈추며 이전 묶음의 색인은 비웁니다. Unicode/리터럴 AND·인용 경계·첫 결과 순서·분석 버전 검사·취소 규칙은 유지합니다. SQLite의 기존 NUL 종료 처리와도 호환합니다.

단일 Linux 환경에서 같은 합성 본문 100만/200만/400만 자의 마지막 인용 조회가 각각 약 0.117/0.523/1.856초에서 0.009/0.018/0.030초로 줄었습니다. 이는 OS 캐시를 비우지 않은 단일 측정이며 실제 사용자 PC나 복잡 문서의 응답 시간·메모리 상한을 보장하지 않습니다. 전체 본문의 일회 메모리 로드와 현재 DB 읽기 호출 대기는 남습니다.

```bash
python -m benchmarks.citation_search --chunks 2000 --output citation-benchmark.json
```

이 명령은 임시 폴더/DB에 약 400만 자의 합성 텍스트와 2,001개 인용을 만들고 앞부분·마지막·미일치 조회 위치를 검증합니다. 기존 파일/DB는 사용하지 않습니다. 집계 JSON에는 문자 수·인용 수·조회 시간·DB 크기를 기록하고 원문·임시 경로는 넣지 않습니다. `--chunks`는 1~10000 사이이며 본문의 2,000자 구간 수입니다.

### 7.23 검색 입력 검증과 오류 복구

본문·파일명·통합 검색 및 일치 인용 조회는 앞뒤 공백을 제외해 **최대 4,096자·공백으로 구분한 검색어 100개**까지 지원합니다. 줄바꿈·탭·Unicode 공백도 기존처럼 검색어 구분에 사용합니다. NUL과 올바르지 않은 Unicode는 거부합니다. 정상 입력의 리터럴 AND·파일명 부분 일치·Unicode 규칙은 유지하며 검색어를 조용히 잘라서 실행하지 않습니다.

제한을 넘는 입력은 DB 생성·색인이나 SQL 실행 전에 오류로 안내합니다. 긴 검색어 때문에 SQLite 식 깊이 제한 오류가 발생하던 문제를 방지합니다. GUI에서는 작업 시작 전에 검사하므로 기존 결과 목록·선택·미리보기·관련 그래프와 탐색 기록을 유지합니다. 입력을 수정하면 정상 검색을 다시 실행할 수 있습니다. CLI 검색의 표준 출력·오류는 UTF-8이며 잘못된 입력은 사용법 오류 코드 2로 종료합니다.

기존 DB·저장 본문·인용·캐시 버전은 바꾸지 않으며 재분석은 필요하지 않습니다. 결과 건수 API는 1~1000 정수만 허용하고 `True`/`False`는 정수 결과 건수로 취급하지 않습니다.

### 7.24 승인 기반 OpenAI 문서 질의응답 (CLI)

외부 AI는 기본 비활성화입니다. 기존 스캔·분석·검색·GUI는 API 키 없이 계속 동작합니다. CLI 사용법은 아래에, GUI 사용법은 7.25에 안내합니다. 임베딩 의미 검색·자동 문서 선정은 후속 작업입니다. 선택한 저장 인용으로 질문하거나 요약을 요청할 수 있으며, 전체 문서를 자동 업로드하지 않습니다.

먼저 검색 결과의 `file_id`와 7.15의 인용 번호를 확인합니다. 아래 명령은 **로컬 미리보기만 수행**하며 키나 네트워크가 필요하지 않습니다. `--source 파일ID:인용번호`를 반복해 중복 없이 최대 4개 인용(각 2,000자, 합계 8,000자)을 선택합니다. 질문은 최대 2,000자입니다. 질문을 명령행 기록에 남기지 않으려면 `--question`을 생략하고 실행 후 입력하세요.

```bat
python -m app.ask_document --source 1:1 --question "이 인용에서 정한 일정은?"
```

실제 요청에는 별도의 OpenAI API 키와 사용료가 필요합니다. ChatGPT 구독과 API 결제는 별개입니다. `OPENAI_API_KEY`는 현재 터미널의 환경변수 또는 별도 비밀정보 관리 방식으로 주입하세요. 키를 소스·명령행 인자·공유 로그·설정 JSON에 저장하지 마세요. `.env` 자동 읽기는 제공하지 않습니다.

Windows CMD에서 활성화 후 같은 요청에 `--send`를 추가합니다 (PowerShell은 `$env:FILE_NETWORK_AI_ENABLED="1"`). 기본 모델은 `gpt-4.1-mini`이며 `--model` 또는 `FILE_NETWORK_OPENAI_MODEL`로 해당 계정에서 사용할 수 있는 구조화 출력 지원 모델을 지정할 수 있습니다.

```bat
set FILE_NETWORK_AI_ENABLED=1
python -m app.ask_document --source 1:1 --source 2:3 --question "두 인용의 일정 차이는?" --send
```

전송 대상 URL·모델·정책 안내·로컬 파일과 인용·**실제 전송 JSON 전체**를 표시합니다. 질문과 선택한 인용 본문만 `S1` 등의 별칭으로 전송하며, 로컬 경로·파일명·시트명·분석 시각·DB·원본 파일은 전송하지 않습니다. 다만 **본문이나 질문 자체에 파일명·이름·주소 등이 들어 있으면 그 내용은 포함**되므로 직접 확인해야 합니다. 표시된 `전송 <요청 확인 코드>`를 대화형 터미널에서 정확히 입력한 경우에만 한 번 호출합니다. 취소·파이프 입력·내용 변경·검토 후 로컬 재분석/삭제/이동은 거부합니다. 승인은 해당 질문·모델·인용 내용에 묶이며 다음 실행에 자동 저장하지 않습니다.

이메일·한국 휴대전화·주민번호 형태·긴 카드번호 형태·일부 인증키/암호·기밀 표시를 질문과 선택 본문에서 탐지하면 **우회 옵션 없이 차단**합니다. 불필요한 메타데이터는 제외하지만 이름·주소의 자동 비식별화, 모든 인증정보 탐지, 포괄적 DLP는 제공하지 않습니다. 패턴 오탐·누락이 가능하므로 민감하거나 기밀인 문서는 전송하지 마세요. 일반 인용 하나라도 민감정보를 포함하면 요청 전체를 차단합니다.

HTTPS의 고정된 `api.openai.com/v1/chat/completions`만 사용하며 리디렉션·도구 실행·자동 재시도·파일 업로드는 하지 않습니다. `store=false`, 최대 출력 토큰 1,500, 응답 최대 64KiB, 소켓 대기 30초/전체 처리 목표 60초를 적용합니다. 네트워크 요청 중 즉시 취소는 보장하지 않으며 Ctrl+C·시간 초과·연결 오류에서도 이미 전달되거나 과금되었을 수 있습니다. 자동 재시도하지 않습니다.

[OpenAI 데이터 정책](https://developers.openai.com/api/docs/guides/your-data)을 2026-11-18 확인했습니다. API 데이터는 기본적으로 모델 학습에 사용되지 않지만 악용 방지 로그는 통상 최대 30일 보관될 수 있으며 법적 요구·계정별 정책에 따라 달라질 수 있습니다. **`store=false`는 무보관이나 Zero Data Retention을 보장하지 않습니다.** 사용 전 최신 제공 업체 정책과 계정 설정을 확인하세요.

답변은 JSON으로 출력하며 사용한 인용을 로컬 `file_id`·0부터 시작하는 `segment`·분석 시각·페이지/시트/슬라이드 근거와 연결합니다. 제공하지 않은 인용 ID·거부·잘린 응답·잘못된 형식은 오류로 처리합니다. 인용 ID 검증은 답변의 사실성을 보장하지 않습니다. AI 답변은 참고용이며 원문 근거를 확인하세요. AI가 파일을 열거나 수정하거나 DB 내용을 변경하는 도구는 제공하지 않습니다. 답변·질문·본문·키는 자동 저장하지 않습니다.

현재 DB의 `ai_transmissions`에는 시각·OpenAI/모델·대상 파일 ID/인용 번호·본문 문자 수·무작위 요청 ID·상태만 기록합니다. 전송 전에 `attempted`를 기록하지 못하면 호출하지 않습니다. 정상 응답은 `succeeded`, 오류·중단은 `failed_or_unknown`이며 후속 기록 실패나 프로세스 강제 종료 시 `attempted`가 남을 수 있습니다. 이 기록만으로 업체 수신·과금·삭제 여부를 확정할 수 없습니다. 원문·경로·답변·키·HTTP 오류 본문은 기록하지 않습니다. DB 내용·인용·추출기 버전은 바꾸지 않아 기존 문서 재분석이 필요하지 않습니다.

API 통신은 모의 응답으로 자동 검증하며, 개발/CI에서 실제 문서를 전송하거나 유료 API를 호출하지 않습니다. 실제 키를 가진 환경의 최종 연결 검증은 별도입니다. CLI 외부 기능을 끄려면 `FILE_NETWORK_AI_ENABLED`를 삭제하거나 `0`으로 설정합니다. GUI는 매번 별도의 창에서 외부 AI 허용을 선택해야 하며 환경변수만으로 자동 활성화하지 않습니다.

### 7.25 AI 질문·요약·비교 GUI

1. 폴더를 분석한 뒤 검색 결과 또는 분석 내역에서 파일을 선택하고 **AI 질문**을 누릅니다. 로컬 검색 결과는 그대로 유지됩니다.
2. 문서 목록과 **인용 번호**를 선택하고 **근거에 추가**를 누릅니다. 기본 인용 번호는 1이며, 다른 번호·다른 문서를 반복 선택해 최대 4개를 추가할 수 있습니다. 인용 번호와 원본 위치는 기존 본문 미리보기의 **인용 단위 · 원본 위치** 모드에서도 확인합니다. 없는 번호·미분석 문서는 미리보기 단계에서 거부합니다.
3. 질문을 입력합니다. 예: `선택한 인용의 일정을 요약해줘`, `두 문서 인용에서 정한 마감일을 비교해줘`. **전송 내용 미리보기 · 호출 없음**을 누르면 대상·질문·선택 본문·모델을 확인할 수 있습니다. **전송 JSON 상세**에는 실제 전송 내용을 표시합니다. 이 단계까지 키·네트워크가 필요하지 않습니다.
4. 실제로 호출할 때만 **OpenAI API 키** 칸에 본인 키를 입력합니다. 비우면 `OPENAI_API_KEY` 환경변수를 사용합니다. 입력은 비밀번호 형태로 표시하고 **현재 창의 메모리에서만 사용**합니다. 창을 닫으면 입력을 비우며 키·질문·본문·답변을 GUI 설정에 저장하지 않습니다. OS 자격 증명 저장소를 통한 영구 보관은 아직 제공하지 않습니다. 키를 채팅·저장소·공유 스크린샷에 보내지 마세요.
5. **이 창에서 외부 AI 사용 허용**과 **질문·선택 본문을 확인했으며 전송·사용료에 동의**를 선택한 뒤 **승인한 내용 한 번 전송**을 누릅니다. 매번 기본 비활성화이며, `FILE_NETWORK_AI_ENABLED` 환경변수만으로 GUI 전송을 활성화하지 않습니다. 질문·모델·근거 변경은 미리보기와 승인을 무효화하고, 키·외부 허용 변경은 승인을 해제합니다.
6. **답변·로컬 근거** 탭에 원래 질문과 답변을 표시합니다. 근거를 선택하고 **선택 근거 본문 확인 · 로컬**을 누르면 답변에 연결된 분석 시점의 본문을 읽습니다. 재분석·삭제 후 이전 버전은 표시하지 않습니다. 경로·인용 번호·PDF 페이지·Excel 시트·PowerPoint 슬라이드 위치는 로컬 안내이며 전송 JSON에 추가하지 않습니다.

요청은 백그라운드에서 실행합니다. 중복 클릭·자동 재시도는 없으며 성공·오류 후 새 요청은 다시 미리보기와 승인을 거칩니다. 호출 중 **닫기**·Escape·부모 창 닫기는 실행 스레드 종료를 기다립니다. 아직 전송 전이면 취소를 검사하지만 **이미 전송된 요청은 회수하거나 과금을 취소할 수 없습니다.** 네트워크 대기 중 즉시 닫힘을 보장하지 않습니다. 실행 도중 UI를 바꾸거나 새 요청을 겹쳐 보낼 수 없습니다.

7.24의 크기 제한·민감정보 차단·업체 정책·원문 없는 전송 기록이 GUI에도 적용됩니다. **선택 인용에 한정된 답변**이며 전체 문서 요약·자동 문서 선택·의미 검색은 아닙니다. 여러 문서의 선택 인용에 대한 비교는 질문으로 요청할 수 있지만 모든 차이를 검출한다고 보장하지 않습니다. AI 답변은 참고용이며 실제 근거를 확인하세요.

GUI 통합 테스트는 모의 API 응답을 사용하며, 배포 자체 검증에는 키 없는 로컬 AI 미리보기만 추가했습니다. 실제 유료 API 연결은 본인 키를 설정한 환경에서 별도로 확인해야 합니다. 일반 CI에서는 EXE·ZIP을 생성하지 않습니다.

### MVP 범위

## 9. Git 협업 규칙

프로젝트 변경 사항은 Issue를 기반으로 관리하며, 기능 개발과 수정은 별도 브랜치에서 진행합니다.

### 9.1 Issue

제목 형식:

```text
[Type] 작업 내용
```

| Type | 설명 |
|---|---|
| Feature | 신규 기능 |
| Bug | 버그 수정 |
| Refactor | 코드 구조 개선 |
| Test | 테스트 작성 및 개선 |
| CI | CI/CD 및 자동화 |
| Docs | 문서 수정 |
| Chore | 기타 설정 및 유지보수 |

Issue에는 작업 배경, 목표, 세부 작업, 완료 조건을 포함합니다.

### 9.2 Branch

브랜치 이름 형식:

```text
type/issue-number-description
```

예시:

```text
feature/12-content-analyzer
fix/15-symlink-scan
test/18-scanner-test
docs/20-readme-update
```

- `main` 브랜치에 직접 작업하지 않습니다.
- Issue에 연결된 별도 브랜치에서 작업합니다.

### 9.3 Commit

커밋 메시지 형식:

```text
type: 작업 내용
```

예시:

```text
feat: add document content extraction
fix: handle inaccessible directories
refactor: separate scanner logic
test: add incremental scan tests
docs: update readme
```

### 9.4 Pull Request

모든 변경 사항은 Pull Request를 통해 `main`에 반영합니다.

PR에는 관련 Issue, 주요 변경 사항, 테스트 결과 및 확인 사항을 포함합니다. 관련 Issue는 `Closes #이슈번호`로 연결합니다.

## 10. 개발 원칙

1. 원본 파일을 임의로 수정하거나 삭제하지 않습니다.
2. 파일 메타데이터와 분석 데이터는 로컬에서 관리합니다.
3. 파일 스캔과 DB 관리 기능은 생성형 AI API에 의존하지 않습니다.
4. AI에는 사용자가 허용한 최소한의 데이터만 전달합니다.
5. 민감정보와 기밀 데이터는 외부 전송을 기본적으로 제한합니다.
6. AI 분석 결과를 DB에 반영할 때는 로컬 엔진에서 검증합니다.
7. 파일 간 관계와 AI 분석 결과의 근거를 추적할 수 있도록 설계합니다.
8. 기능을 추가할 때 테스트와 문서를 함께 갱신합니다.
